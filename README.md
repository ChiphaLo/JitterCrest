# JitterCrest

[简体中文](README.zh-CN.md) | English

JitterCrest is a self-hosted network quality tool. One main site serves the web page;
measurement nodes exchange traffic with the browser directly and report speed, RTT,
jitter, packet loss and stability.

## Technology

- **Backend**: C++20, Boost.Asio coroutines and Boost.Beast HTTP, OpenSSL, a built-in
  TLS + HTTP/2 listener (nghttp2), WebRTC DataChannels (libdatachannel), libcurl and
  nlohmann-json.
- **Frontend**: one HTML file with Web Workers, streaming Fetch, WebRTC and Canvas/SVG
  charts, embedded in the server executable; no JavaScript build step.
- **Deployment**: CMake + Ninja, Docker, Caddy and systemd. Nodes join a main site
  through commands generated by its `/admin` page.

## Measurement methods

All tests run between the browser and the selected node. The formulas below match
`public/index.html` and the node's receipt counters.

### Download and upload speed

Both directions use the same receiver-side window. The receiver (the browser for
download, the node for upload) takes the arrival time $t_0$ of the first payload byte,
skips a warm-up of $W = 1\ \mathrm{s}$ and then counts bytes for exactly $T = 10\ \mathrm{s}$.
Bytes that arrive outside the window are ignored; the sender stops when the window closes.
Download reads HTTP response streams. Upload sends a streaming HTTP/2 request body
(browsers without request streams send repeated 4 MiB requests), and the node reports
its counters every 100 ms.

```math
v = \frac{8\,B\big([t_0+W,\ t_0+W+T)\big)}{10^{6}\,T}\ \ \mathrm{Mbit/s}
```

$B(\cdot)$ is the number of payload bytes received in the interval; times are in seconds.
The chart samples the same counter every $\Delta = 100\ \mathrm{ms}$ and draws a 0.5 s
rolling mean weighted by each sample's overlap $o_i$ with the last 0.5 s:

```math
v_k = \frac{8\,\Delta B_k}{10^{6}\,\Delta t_k},\qquad
\bar v = \frac{8\sum_i B_i\,o_i/\Delta t_i}{10^{6}\sum_i o_i}
```

The end-to-end rate also includes the warm-up:
$v_{\mathrm{e2e}} = 8 B_{\mathrm{total}} / \big(10^{6} (t_{\mathrm{end}} - t_0)\big)$.
Multi-stream runs add the bytes of all streams to one counter.

### RTT and jitter

The probe uses an unordered DataChannel without retransmission (UDP-like) and sends
20 packets/s for 2 s in both directions at the same time. Each RTT is measured on one
clock, so no clock synchronisation is needed:

- **Upload RTT**: the browser sends a sequence number and timestamp; the node echoes
  it; $r = t_{\mathrm{echo}} - t_{\mathrm{send}}$ on the browser clock.
- **Download RTT**: the node sends; the browser echoes; the node measures $r$ on its
  own clock and returns the samples.

For the $n$ samples of one direction, sorted as $r_{(0)} \le \dots \le r_{(n-1)}$:

```math
P_p = r_{(\lfloor (n-1)p \rfloor)},\qquad
J_{\mathrm{MAD}} = 1.4826\cdot P_{50}\big(\left| r_i - P_{50} \right|\big),\qquad
J_{\Delta} = \frac{1}{n-1}\sum_{i=2}^{n} \left| r_i - r_{i-1} \right|
```

$J_{\mathrm{MAD}}$ is a robust jitter that scales to a standard deviation for normal
noise; $J_{\Delta}$ is the mean change between consecutive samples. The page also
reports min, mean, max, P95 and P99.

### Stability test

The stability test runs the same paired probe at $R \in \lbrace 20, 60, 100, 200 \rbrace$ packets/s
for 10–60 s (default 100 packets/s for 10 s). With packet interval
$\tau = 1000/R\ \mathrm{ms}$ and $N$ packets sent in one direction:

```math
L = \frac{N_{\mathrm{missing}}}{N},\qquad
L_{\mathrm{eq}} = \frac{N_{\mathrm{missing}} + N_{r>200\,\mathrm{ms}}}{N},\qquad
O = \frac{N_{\mathrm{reordered}}}{N}
```

- **Late** packets have $r > 100\ \mathrm{ms}$. Missing packets and packets with
  $r > 200\ \mathrm{ms}$ are drop-equivalent; a burst is a run of $k$ consecutive
  drop-equivalent sequence numbers and lasts $k\tau$.
- **Reordering** counts packets that arrive after a higher sequence number.
- **Local delay** marks packets whose browser handler ran after a gap longer than
  $\max(50\ \mathrm{ms},\ 8\tau)$ with at least three handlers in 8 ms. They are
  reported separately and excluded from network drop-equivalents.

Lag spikes use a threshold that adapts to the baseline $B = P_{50}$, the robust jitter
$J = J_{\mathrm{MAD}}$ and the tail $Q = P_{95} - P_{50}$, where
$\mathrm{clamp}(x, a, b) = \min(\max(x, a), b)$:

```math
\begin{aligned}
s &= \sqrt{(J/10)^2 + (Q/45)^2} \\
\theta &= B + m + (M - m)\left(1 - e^{-0.45\,s^{1.3}}\right),
\quad m = \mathrm{clamp}(0.35B, 15, 30),\ M = \mathrm{clamp}(0.65B, 28, 60) \\
\theta_s &= \max\!\left(\theta + 25,\ B + m_s + (M_s - m_s)\left(1 - e^{-0.35\,s^{1.25}}\right),\ 110\right),
\quad m_s = \mathrm{clamp}(0.9B, 50, 90),\ M_s = \mathrm{clamp}(1.25B, 80, 130)
\end{aligned}
```

All values are in milliseconds. Samples with $r \ge \theta$ are impact samples and
samples with $r \ge \theta_s$ are severe spikes. The page reports their rates
$N_{r\ge\theta}/n$ and $N_{r\ge\theta_s}/n$, the impact events and the longest impact
run $k_{\max}\tau$.

## Quick start

```sh
CC=clang-18 CXX=clang++-18 bash cpp/cmake/bootstrap-datachannel.sh /absolute/local/deps
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_COMPILER=clang++-18 -DCMAKE_PREFIX_PATH=/absolute/local/deps/install
cmake --build build --parallel 2 && ctest --test-dir build --output-on-failure
SPEEDTEST_HOST=127.0.0.1 PORT=32132 build/cpp/speedtest-cpp
```

For a main site with nodes, run `python3 cpp/deploy/quickstart.py`, then add nodes from
`/admin`.
